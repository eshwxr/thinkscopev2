Planner

app/planner.py
Breaks the question into a plan before touching any documents.
user query ⇢ sub-q 1 sub-q 2 sub-q 3
  • Decomposes the query into 1–3 focused sub-questions that together answer it fully.
  • Narrow questions pass through untouched — no forced decomposition.
  • Returns strict JSON; any malformed output degrades gracefully to the original query.
in user query out 1–3 sub-questions 1 LLM call
reformulated query · max ×2

Hybrid Retrieval

app/hybrid_retrieval.py
Two search engines vote, and their disagreement is the feature.
dense · MiniLM ⇢ RRF fuse · top-8 ⇠ sparse · BM25
  • Dense: all-MiniLM-L6-v2 embeddings over 110 papers / 6k chunks in ChromaDB — catches meaning, misses exact terms.
  • Sparse: BM25 keyword index — catches exact terms, misses paraphrases.
  • Both rankings fused with Reciprocal Rank Fusion (k=60) from a 20-candidate pool each.
  • On retries, new chunks accumulate with earlier ones (deduped, capped at 12) instead of replacing them.
in sub-question out top-8 fused chunks 0 LLM calls

Critic

app/critic.py · app/graph.py
The self-doubt stage — decides whether retrieval actually worked.
insufficient ⟲ reformulate retry → sufficient ✓ continue
  • Judges whether the accumulated chunks are sufficient to answer correctly — not exhaustively.
  • On fail: writes a reformulated search query and loops back to Retrieval — at most twice, then falls through with best-effort chunks. Never loops forever.
  • The whole loop is a LangGraph state machine: retrieve → critique → (retry | continue).
in sub-question + chunks out pass / fail + new query 1 LLM call per attempt
⟲ critic fail → reformulated query → retrieval (max ×2)

Cited Synthesis

app/citation_verifier.py
No free-form prose allowed — every sentence must name its source.
“RRF fuses the two rankings…” [2404.07220_chunk3]
“BM25 catches exact-term matches…” [2108.06279_chunk25]
“Dense retrieval covers paraphrases…” [2502.01113_chunk103]
  • Writes the answer as individual claims, one sentence each.
  • Each claim is tagged with the exact chunk ID it came from.
  • A claim it can't attribute to a chunk doesn't get written.
in sub-question + chunks out claims, each with chunk ID 1 LLM call

Citation Verifier

app/citation_verifier.py
An independent fact-checker with no loyalty to the writer.
✓ claim 1 — supported by its cited chunk
✓ claim 2 — supported by its cited chunk
✕ claim 3 — flagged UNVERIFIED, kept visible
  • For every claim, a separate LLM call reads only the cited chunk and asks: does this text actually support this claim?
  • Claims that fail get a visible UNVERIFIED badge — they're flagged, not silently dropped.
  • This is what moved verified-claim rate from 23% (free-form) to 90% (cited) in Phase 4 testing.
in claim + its cited chunk out verified / unverified 1 LLM call per claim
✓ grounded answer · per-claim verification · latency report
